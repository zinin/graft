# graft на Windows: дизайн

Дата: 2026-11-27. graft v0.4.0, Claude Code 2.1.332, Go 1.26 по `go.mod`.

## Зачем

Владелец иногда работает в Windows и хочет там тот же graft, что на Linux: запускать его из PowerShell или Windows Terminal, с нативным `claude.exe` от официального установщика (`irm https://claude.ai/install.ps1 | iex`). В WSL Linux-сборка работает уже сейчас, но это другой сценарий.

## Что мешает сейчас

- Сборка под Windows падает в одном месте: `cmd/graft/ui.go:105`, поле `Setsid` у `syscall.SysProcAttr`. `go vet` ещё находит `syscall.Kill` в `internal/launch/run_test.go` и `syscall.Mkfifo` в `internal/ui/keys_test.go`.
- Прямой режим заменяет graft на `claude` через `syscall.Exec`. В Windows этот вызов только возвращает ошибку «not supported by windows».
- Ключ `command` запускается через `/bin/sh -c`.
- Проверка «файл ключа читают другие» смотрит на биты прав. В Windows Go показывает у любого файла 0666 или 0444, поэтому предупреждение было бы всегда.
- Имена переменных окружения в Windows не различают регистр, а graft сравнивает их точно: `anthropic_api_key` из оболочки дошёл бы до Claude Code, который в Windows читает переменные без учёта регистра.
- Каталог `.claude` graft ищет через `HOME`.
- `graft ui` открывает браузер через `xdg-open` или `open`, а команды, которые страница предлагает скопировать, написаны для POSIX shell.
- `install.sh`, архивы tar.gz, CI и тестовые подделки `claude` (shell-скрипт, символическая ссылка) рассчитаны на Unix.

## Цели

1. В нативной Windows 10 и 11, x64 и ARM64, работает всё, что есть на Linux: `graft PROFILE`, `--dry-run`, `list`, `check`, `ui`; прямой режим, роутер, агенты, подписка. Формат конфига тот же.
2. graft ставится одной командой PowerShell, в релизе есть zip для Windows.
3. CI гоняет тесты на Windows. Поведение на Linux и macOS не меняется, кроме решений, отмеченных ниже.
4. Документация описывает Windows: установку, пути, `command` и чем отличается безопасность.

## Не цели

- Отдельная работа под WSL.
- Запуск `claude.cmd` или `claude.bat`, которые кладёт в PATH npm.
- 32-битная Windows: её не поддерживает и Claude Code.
- Пакеты winget и scoop, подпись `graft.exe` (Authenticode). Владелец запускает graft на своём компьютере, сертификата у него нет. Компьютеры под управлением компании, где неподписанные программы запрещены (Smart App Control, WDAC, AppLocker) или стоит EDR, — не цель: там `graft.exe` может не запуститься.
- Проверка ACL файлов ключей и закрытые ACL на файлах, которые пишет graft: это вариант 2, его можно добавить позже.
- Проверка в `graft ui`, чьи процессы к нему подключаются: на Windows её нет, как и на macOS.
- Передача сигналов `claude` на Windows: консольные события он получает сам.

## Провалом было бы

- graft на Windows передаёт аргументы через cmd.exe: JSON в `--settings` и `--agents` ломается, а `&`, `|` и `%` в описании модели cmd.exe понимает по-своему.
- Переменная, которую graft убирает (`ANTHROPIC_API_KEY` и другие), доходит до `claude`, потому что написана в другом регистре.
- На Linux и macOS изменилось поведение или ослабли проверки.
- graft меняет PATH, файлы Claude Code или файлы оболочки.
- Ctrl+C или закрытие окна убивает graft раньше `claude`, и сессия теряет роутер.

## Ограничения

- Только стандартная библиотека и `go.yaml.in/yaml/v3`; вариант 1 не требует `golang.org/x/sys`. Go 1.26 по `go.mod`.
- В Windows процесс нельзя заменить другим: `syscall.Exec` возвращает ошибку.
- `os.Process.Signal` в Windows умеет только `Kill`. Ctrl+C и Ctrl+Break консоль шлёт всем своим процессам; Go отдаёт их как `os.Interrupt`. Закрытие окна, выход из системы и выключение приходят как `syscall.SIGTERM`, после чего у процесса около 5 секунд.
- Аргументы процесса в Windows — одна строка. `.cmd` и `.bat` запускает cmd.exe, и `os/exec` экранирует их аргументы неверно ([golang/go#69939](https://github.com/golang/go/issues/69939)).
- Имена переменных окружения в Windows без учёта регистра. Запуская дочерний процесс, Go из одноимённых переменных оставляет последнюю.
- Нативный установщик Claude Code кладёт `claude.exe` в `%USERPROFILE%\.local\bin`, версии в `%USERPROFILE%\.local\share\claude` и PATH не меняет. npm-пакет ставит тот же `claude.exe`, но в PATH попадает обёртка `claude.cmd`.
- Без Git for Windows Claude Code выполняет команды через PowerShell. `sh` есть не всегда: Git for Windows кладёт в PATH только `Git\cmd`.
- Git for Windows по умолчанию ставит `core.autocrlf=true` (на виртуалке так и есть). Раннеры GitHub для Windows тоже, поэтому без `.gitattributes` файлы приходят с CRLF.
- Права на `C:\Users\<имя>` по умолчанию: SYSTEM, Administrators и сам пользователь, с наследованием (проверено на виртуалке).
- Windows OpenSSH задаёт `SSH_CONNECTION` (проверено): `graft ui` по SSH не открывает браузер, как и на Unix.

## Подходы

Выбирали, как защищать ключи. Всё остальное от этого выбора не зависит.

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| **1. Как на macOS** | новых зависимостей нет; кода только для Windows почти нет; ключи по умолчанию лежат в профиле, а он закрыт от других пользователей | ключ вне профиля (например, `D:\keys`) на машине с несколькими пользователями может быть открыт, и graft об этом не скажет |
| 2. ACL как на Linux | предупреждение о файле ключа, который могут читать другие, с командой `icacls`; Save key создаёт файл, доступный только владельцу, где бы ни лежал конфиг | вторая зависимость (`golang.org/x/sys/windows`); пара сотен строк кода только для Windows, которые проверяет только CI на Windows |

Отброшены:
- только документация про WSL: не даёт нативной Windows;
- предупреждение для ключа вне `%USERPROFILE%` по одному пути: ошибается в обе стороны, и для закрытой папки на `D:\`, и для открытой папки в профиле;
- проверка соединений в `graft ui` через таблицу TCP: обычный пользователь Windows не может открыть чужой процесс и прочитать его аргументы, поэтому адрес с токеном ему не виден. Это проверяется на виртуалке, см. ниже.

Владелец выбрал **1**: graft нужен ему на своей машине, а 2 защищает только ключ вне профиля на машине с несколькими пользователями. Если понадобится, 2 ляжет сверху, остальное не изменится.

## Как это устроено

Код, который на другой системе не компилируется, уходит в файлы `_windows.go` и `_unix.go` (или под теги сборки). Мелкие различия решаются через `runtime.GOOS`.

### Запуск `claude`

**Поиск.** В Windows graft ищет в PATH именно `claude.exe` (`exec.LookPath("claude.exe")`), а не `claude`. Поэтому `claude.cmd` и `claude.bat` не запускаются никогда, даже если стоят в PATH раньше. Если `claude.exe` нет, а `claude.cmd` или `claude.bat` есть, graft отказывается с понятной ошибкой: этот `claude` — пакетный файл, cmd.exe испортил бы аргументы graft, поставьте Claude Code нативным установщиком (`irm https://claude.ai/install.ps1 | iex`). Так же ведут себя запуск, `--dry-run`, `check` и предпросмотр в `graft ui`.

**Прямой режим.** В Windows graft запускает `claude.exe` дочерним процессом с аргументами и окружением плана, отдаёт ему свою консоль (stdin, stdout, stderr), ждёт и выходит с его кодом. Роутера нет, ключ провайдера в окружении `claude`, как и на Unix. Пока `claude` работает, graft ловит и пропускает `os.Interrupt` и `SIGTERM`: консоль присылает их и `claude`, а он с ними разбирается сам. На Unix всё остаётся как есть: `exec`.

**Роутер.** Как сейчас. В Windows graft ловит `os.Interrupt` и `SIGTERM`, ничего не пересылает и ждёт `claude`. Код выхода равен коду `claude`: формы 128+N в Windows нет.

Если graft убьют (`taskkill /F`), `claude` останется без роутера, как после `SIGKILL` на Unix. Это пишется в limitations.

### Переменные окружения

- В Windows graft сравнивает имена переменных без учёта регистра везде, где ищет, убирает или задаёт переменную: `system.lookupEnv`, `plan.lookup`, `plan.unset`, `launch.Environ`, слияние `NO_PROXY`. Тогда `anthropic_api_key` из оболочки убирается так же, как `ANTHROPIC_API_KEY`.
- Проверка в `env` конфига, что переменной не управляет graft (`config.OwnedEnv` и прочие), идёт без учёта регистра на всех системах: на Linux `anthropic_base_url` ничего не значит, а в Windows это та же переменная. В Windows конфиг ещё и отвергает в одном `env` два имени, которые различаются только регистром.
- `NO_PROXY` и `no_proxy` в Windows — одна переменная. graft по-прежнему задаёт обе с одним значением, как на Unix: Go оставит одну, и Claude Code прочтёт её под любым именем. `NO_PROXY` из `env` профиля в любом регистре вливается в значение graft, а не перекрывает его.
- Домашний каталог для `.claude`. Claude Code в Windows берёт его из `USERPROFILE`, а `HOME` не смотрит (проверено на виртуалке: с разными `USERPROFILE` и `HOME` `claude.exe` создал `.claude` и `.claude.json` в `USERPROFILE`). Поэтому `plan.UserSettingsDir` в Windows смотрит `USERPROFILE` в `env` профиля, в `defaults` и в окружении, а сообщения называют `USERPROFILE`, а не `HOME`.

### Пути

- Пути те же, что на Unix, от `%USERPROFILE%` (`os.UserHomeDir`): конфиг `~/.config/graft/config.yaml` (или `XDG_CONFIG_HOME`, `GRAFT_CONFIG`, `--config`), лог `~/.local/state/graft/graft.log` (или `XDG_STATE_HOME`), ключи `keys\` рядом с конфигом.
- В Windows `~/` и `~\` в начале пути одинаково означают домашний каталог: в путях конфига и в `--config`.
- В Windows graft показывает все пути с прямыми слэшами: внутри домашнего каталога как `~/…` (`~/.config/graft/keys/ollama`), остальные как `D:/keys/ollama`. Windows принимает `/`, конфиг, записанный `graft ui`, одинаков на обеих системах, а логика путей на странице (`keysDir`, имя файла в `layout.js`) работает с `/` и не меняется. Начало пути `config.Tildify` в Windows сравнивает без учёта регистра.
- В YAML обратный слэш в кавычках `"..."` — экранирование. Документация советует писать пути с `/`, без кавычек или в одинарных кавычках.
- Ротация лога. В Windows нельзя переименовать открытый файл, а лог может писать другая сессия. Если переименовать не вышло, graft продолжает писать в текущий лог, а не теряет его.

### Ключи

- `command` в Windows выполняется через Windows PowerShell: `powershell.exe -NoLogo -NoProfile -Command <команда>`, одним аргументом, который экранирует `os/exec`. `-EncodedCommand` не берём: антивирусы и EDR считают его признаком вредоноса. `-ExecutionPolicy Bypass` тоже не берём: команда работает при той же политике, что и PowerShell пользователя, и модуль, который грузится у него в консоли (например, SecretManagement), загрузится и здесь. stdin и stderr — терминал, как на Unix, чтобы менеджер паролей мог спросить пароль. Ключ — то, что команда напечатала, с обрезкой пробелов по краям. PowerShell 5.1 взят потому, что он есть в любой Windows; `pwsh` можно позвать из самой команды.
- В Windows нет предупреждения о правах на файл ключа (вариант 1). Документация: держите ключи в профиле.
- Файл ключа в UTF-16 (так пишут `>` и `Out-File` в PowerShell 5.1) даёт понятную ошибку на всех системах: файл в UTF-16, сохраните его как ASCII или UTF-8 без BOM. Сейчас ошибка говорит про U+FFFD.
- Save key в `graft ui` пишет файл как сейчас: временный файл, затем жёсткая ссылка или переименование. Режимы 0600 и 0700 Go в Windows не применяет (кроме флага «только чтение»), и файл получает права папки, в профиле закрытые.

### `graft ui`

- В Windows браузер открывается через `rundll32.exe url.dll,FileProtocolHandler <адрес>`, без cmd.exe. Токен стоит во фрагменте адреса (`#token=`), и он должен дойти до браузера: проверить на виртуалке. `canBrowse` в Windows — да, кроме сессии по SSH.
- Проверки соединений нет (`peer_other.go`); комментарий там называет и Windows.
- Страница узнаёт систему сервера из ответа API состояния и в Windows предлагает команды для PowerShell. Команда для ключа создаёт папку, удаляет старый файл, читает ключ без эха и пишет его одной строкой в ASCII без BOM. Подсказка запуска (`graft --config …`) в кавычках PowerShell. На Linux и macOS команды прежние.
- Пути от сервера приходят с `/`, поэтому логика путей страницы не меняется. Путь, набранный в форме с `\`, команда для ключа отдаёт PowerShell как есть, и папку из него выделяет сам PowerShell (`Split-Path`).
- Конфиг с CRLF: первое сохранение и так переписывает форматирование, и файл выходит с LF. Тест проверяет, что `\r` не попадает ни в значения, ни в комментарии.

### Установка и релиз

- `make dist` собирает ещё `windows/amd64` и `windows/arm64`: `graft_<версия>_windows_<arch>.zip` с `graft.exe`, `LICENSE`, `README.md` и `docs/`, в тот же `SHA256SUMS`.
- `install.ps1` в корне повторяет `install.sh`: `irm https://raw.githubusercontent.com/zinin/graft/master/install.ps1 | iex`. `GRAFT_VERSION` и `GRAFT_INSTALL_DIR` берутся из переменных окружения, по умолчанию папка `%USERPROFILE%\.local\bin`, где лежит и `claude.exe`. Скрипт определяет x64 или ARM64, качает `SHA256SUMS` и zip, сверяет SHA-256, достаёт `graft.exe` и запускает `graft version`. PATH он не меняет: если папки там нет, печатает команду, которая добавит её в PATH пользователя. Работает в Windows PowerShell 5.1 и PowerShell 7. Обходится командлетами (`Invoke-WebRequest`, `Get-FileHash`, `Expand-Archive`) и `$env:`, без вызовов типов .NET; там, где Constrained Language Mode отказывает `Get-FileHash` и `Expand-Archive` (это скрипты, создающие типы .NET), берёт `certutil -hashfile` и `tar.exe`. Весь скрипт — один блок `& { … }`, чтобы под `iex` его функции не оставались в сеансе пользователя. Скрипт целиком читается до запуска, как `main` в `install.sh`.
- `install.sh`, запущенный из Git Bash, MSYS или Cygwin, отвечает, что для Windows есть `install.ps1`.

### CI

- `.gitattributes`: `* text=auto eol=lf`. Тогда выгрузка в Windows хранит LF, и на это не реагируют ни `gofmt`, ни встроенные файлы страницы, ни тесты.
- В матрицу тестов `ci.yml` добавляется `windows-latest`. Проверка `gofmt` идёт только на Linux: форматирование от системы не зависит. На Windows `go test` без `-race`: race detector там требует C-компилятор, а гонки ловят Linux и macOS. Тесты страницы (`node --test`) идут и на Windows.
- Задание установки на Windows (`install.ps1` против последнего релиза) добавляется после первого релиза с архивами Windows. До тех пор `install.ps1` проверяется на виртуалке против архивов `make dist`.

### Тесты

- Тесты только для Unix (сигналы, режимы chmod, FIFO, символические ссылки, ключи-команды POSIX) уходят под теги сборки или пропускаются в Windows.
- У Windows свои тесты: поиск `claude.exe` и отказ от `.cmd`, прямой режим дочерним процессом с кодом выхода, регистр переменных, `USERPROFILE`, ключ-команда PowerShell, отсутствие предупреждения о правах, пути с `~\`, ошибка файла ключа в UTF-16, запасной путь ротации лога.
- Поддельный `claude` — сам тестовый бинарник, скопированный как `claude.exe`: символические ссылки в Windows требуют привилегии. Подделка-скрипт из `TestExecReplacesProcess` тоже становится тестовым бинарником, режим задаёт переменная окружения.
- Где тесты задают `HOME`, в Windows они задают и `USERPROFILE`. Списки в PATH собираются через `os.PathListSeparator`.

### Документация

- README: graft работает на Linux, macOS и Windows; команда установки для Windows.
- `install.md`: раздел про Windows (`install.ps1`, zip, PATH; если `graft.exe` скачан браузером, Windows может предупредить о неподписанном файле).
- `configuration.md`: пути в Windows, `command` через PowerShell, обратные слэши в YAML.
- `how-it-works.md`: прямой режим в Windows, сигналы.
- `security.md`: что в Windows иначе (проверки прав на ключ нет, держите ключи в профиле; в `graft ui` нет проверки соединений и почему; регистр переменных).
- `limitations.md`: `claude.cmd`, graft убит `taskkill /F`.
- `troubleshooting.md`: новые сообщения (пакетный `claude`, ключ в UTF-16, `graft` нет в PATH).
- `web-ui.md`: команды для PowerShell.

## Проверка на виртуалке

Виртуалка владельца: Windows 11 x64 (сборка 26200) в VMware, доступ по SSH, пользователь в Administrators. Есть Git for Windows (`core.autocrlf=true`), PowerShell 7 и Windows PowerShell 5.1. Имя хоста и пути там — в `.superpowers/scratch/windows/wintest.sh`, который git не хранит: в репозиторий они не попадают. Другие машины владельца не трогаем.

Уже сделано, пока писался план:
- поставлены Go 1.27.4 (в папку пользователя, без установщика) и Claude Code 2.1.332 нативным установщиком;
- `wintest.sh` копирует рабочее дерево и гоняет там `go vet` и `go test`; без C-компилятора, поэтому без `-race`;
- на копии, где три Unix-вызова убраны, прогнаны тесты: `edit` и `router` зелёные, остальные падают из-за `HOME` вместо `USERPROFILE`, жёстких путей `/home/u`, проверок chmod, `/bin/sh`, временных папок внутри профиля и из-за поведения, которое меняет этот дизайн. Нашлась и ошибка: `ui.Store.Version` в Windows не замечает файл, переименованный поверх конфига, потому что `os.SameFile` читает номер файла по пути в момент сравнения;
- `claude.exe` берёт домашний каталог из `USERPROFILE`, не из `HOME`;
- ключ-команда через `powershell.exe -NoLogo -NoProfile -Command`, запущенная из Go: `"`, `'`, `$env:`, `&`, `|`, `;` и кириллица работают так же, как набранные в PowerShell; `exit 3` даёт код 3, ошибка или провал внешней команды — код 1;
- на настоящей консоли (`ssh -tt`, ConPTY) `Read-Host` и `Read-Host -AsSecureString` показывают запрос в консоли, а в ключ попадает только напечатанное командой;
- команда для ключа, которую предложит страница, на консоли виртуалки создаёт файл одной строкой в ASCII без BOM.

Осталось:
1. С настоящим `claude.exe`: `graft check`, `list`, `--dry-run`. Прямой профиль и профиль за роутером в режиме `claude -p` против заглушки провайдера на виртуалке: запрос доходит до заглушки с нужной моделью и ключом или секретом сессии, Claude Code принимает JSON из `--settings` и `--agents`, код выхода graft равен коду `claude`. Настоящий провайдер — только если владелец сам положит туда ключ.
2. Живая сессия в консоли (Ctrl+C, код выхода) через `ssh -tt`; закрытие окна и `graft ui` в браузере на рабочем столе виртуалки проверяет владелец.
3. `install.ps1` против архивов `make dist`, которые отдаёт локальный HTTP-сервер на виртуалке (копия скрипта с локальным адресом).
4. Видит ли обычный пользователь аргументы чужих процессов. Создать временного локального пользователя без прав администратора, проверить, что он не видит аргументов процесса владельца (`Win32_Process.CommandLine`), и удалить его. Если видит — остановиться и прийти к владельцу: от этого зависит выбранный подход.

## Решения

Владелец:
- нативная Windows, для своей работы; WSL не в счёт;
- компьютер свой, не управляемый компанией; подписи `graft.exe` не будет;
- подход 1;
- в Windows работает всё то же, что на Linux; пути те же от `%USERPROFILE%`; прямой режим дочерним процессом; `command` через PowerShell; `claude.cmd` не запускается; `graft ui` открывает браузер и даёт команды для PowerShell; zip и `install.ps1` в `%USERPROFILE%\.local\bin`; тесты на Windows в CI; не-цели из списка выше;
- проверки на своей виртуалке с Windows.

Решения исполнителя дизайна (проверьте):
- искать в PATH именно `claude.exe`, а `.cmd` и `.bat` отвергать, только когда `claude.exe` нет;
- Windows PowerShell 5.1 с `-Command`, без `-EncodedCommand` и `-ExecutionPolicy Bypass`;
- `install.ps1` без вызовов .NET, с запасными `certutil` и `tar.exe` для Constrained Language Mode;
- проверка переменных, которыми управляет graft, без учёта регистра на всех системах;
- в Windows graft задаёт и `NO_PROXY`, и `no_proxy`, как на Unix: это одна переменная с одним значением;
- `USERPROFILE` для `.claude` (подтверждено на виртуалке);
- в Windows все пути показываются с `/` (`~/…`, `D:/…`), `~\` тоже понимается;
- `ui.Store.Version` запоминает номер файла сразу после `os.Stat`;
- ротация лога в Windows не теряет лог;
- ошибка про UTF-16 на всех системах;
- после сохранения в `graft ui` конфиг всегда с LF;
- `.gitattributes` с `eol=lf`;
- формат `--dry-run` прежний: он описывает запуск, а не даёт команду для вставки;
- после прямой сессии в Windows нет предупреждения о сохранённой модели, как и на Unix;
- `install.sh` в Git Bash отсылает к `install.ps1`;
- задание установки на Windows в CI — после первого релиза с архивами Windows;
- ARM64 собирается, но запускать его негде.

## Исполнителю

Решает сам: как разложить платформенный код по файлам; тексты сообщений; заглушка провайдера.

Проверяет на виртуалке, прежде чем полагаться: что фрагмент адреса доходит до браузера через `rundll32` (если нет — `explorer.exe <адрес>`); помечает ли `Invoke-WebRequest` скачанный файл как пришедший из интернета.

## Приёмка

- `GOOS=windows go build ./...` и `GOOS=windows go vet ./...` чистые; тесты зелёные на Linux, macOS и Windows в CI и прямо на виртуалке.
- На виртуалке с настоящим `claude.exe` работают прямой режим и роутер (`claude -p` против заглушки), коды выхода верные, `claude.cmd` отвергается, `check`, `list` и `--dry-run` работают.
- `install.ps1` ставит graft на виртуалке из локальных архивов.
- Проверка из пункта 4 подтвердила, что другой пользователь не видит аргументов.
- На Linux и macOS прежние тесты проходят без изменений, кроме мест, где поведение меняют решения выше.
- Документация обновлена.
- Владелец проверил на рабочем столе виртуалки живую сессию и `graft ui` в браузере.
